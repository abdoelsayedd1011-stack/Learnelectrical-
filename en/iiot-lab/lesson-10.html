MQTT

The protocol that carries plant data to your phone. Light enough for a ten-dollar vibration sensor to speak it, robust enough for entire plants to depend on it.

1Publish and subscribe

MQTT is an extremely lightweight IoT protocol: devices never talk to each other directly; both connect to a broker. A publisher sends a message to a topic, and the broker distributes it to everyone who has subscribed to that topic. The publisher does not know who reads, and the subscriber does not know who wrote, so you can add a new dashboard or phone without touching the PLC.

  • Port 1883 is unencrypted; 8883 uses TLS. Common brokers: Mosquitto (free), EMQX, HiveMQ, and the AWS/Azure services.
  • A message = topic + payload (bytes: a number, text, JSON). MQTT does not prescribe the payload format.
  • The connection is always initiated outbound by the client, so it passes through firewalls easily and needs no inbound ports opened at the plant.

2Topics and wildcards

A topic is a string of levels separated by /. Design it to mirror the plant hierarchy:

factory/line3/oven/temperature
  • + matches exactly one level: factory/+/oven/temperature = oven temperature on every line.
  • # matches everything below (last position only): factory/line3/# = everything on line 3.
  • Wildcards are for subscribing only; you always publish to a specific topic.
  • Topics beginning with $SYS/ carry the broker’s own statistics.
  • Avoid spaces and uppercase letters, and do not start a topic with /.

3QoS, Retain and Last Will

QoSGuaranteeUse
0At most once (fire and forget)Frequent readings where losing one is harmless: temperature every second
1At least once (may be duplicated)Alarms and counters; the most widely used
2Exactly once (four-step handshake)Commands and billing; the heaviest
  • Retain: the broker keeps the last message on the topic and sends it immediately to any new subscriber. Essential for state values (is the machine running?) so a dashboard does not have to wait for the next change.
  • Last Will and Testament (LWT): on connecting, the client specifies a “will” message that the broker publishes on its behalf if it disconnects unexpectedly: line3/gateway/status = offline. This is how you tell a dead gateway from a stopped machine.
  • Keep alive: the client sends a heartbeat every N seconds; if none arrives within 1.5 × N, the broker considers it disconnected and publishes the will.
  • Clean session / Persistent: a persistent session retains the client’s subscriptions and the QoS 1/2 messages it missed while disconnected.

4Sparkplug B: MQTT with structure

MQTT defines neither the payload format nor topic names, so every gateway ends up speaking its own dialect. Sparkplug B is an Eclipse specification that imposes a topic structure, spBv1.0/<group>/<type>/<edge node>/<device>, and message types: NBIRTH (node birth, with all its metrics and data types), DDATA (device data, on change only), NDEATH (the will) and NCMD (a command to the node). The payload is compact Protobuf with timestamps. SCADA systems such as Ignition understand it natively and build tags automatically.

Rule of thumb: if you are building from scratch with a system that supports it, use Sparkplug B. Otherwise, choose simple JSON with fixed keys, {"v":182.5,"u":"C","t":1730000000}, and document it.

5Practical examples

  • Try it on your PC: install Mosquitto, then in one window run mosquitto_sub -t "factory/#" -v and in another mosquitto_pub -t factory/line3/oven/temperature -m 182.5 -r.
  • Directly from the PLC: the LMQTT library (Siemens) or MQTT blocks on Beckhoff, Wago and Schneider M262, or via a gateway (Lesson 11), which is the most common approach.
  • Security: a username and password per gateway, TLS on 8883, and an ACL on the broker: the gateway may publish to factory/line3/# only and cannot read other lines.
  • Message volume: report by exception, not every 100 ms. Thousands of sensors × 10 messages/s will swamp any broker.
